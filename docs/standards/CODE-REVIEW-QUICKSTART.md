## ⏱️ 5分钟速览

### 什么是代码审查?

代码审查就是**同事之间互相检查代码**的过程,就像写完作业请同学帮忙检查一样。

**为什么要做代码审查?**
1. **发现bug** - 多双眼睛更容易发现问题
2. **提高质量** - 代码更规范、更易维护
3. **知识共享** - 学习别人的好思路和技巧
4. **团队成长** - 共同进步,提升整体水平

---

## 🎯 审查三原则

1. **对事不对人** - 评论代码,不评论人
2. **先问后判** - 不确定的地方先提问,不要直接批评
3. **有理有据** - 不仅说"有问题",还要说"为什么"和"怎么办"

---

## 🚀 第一次审查

### Step 1: 打开PR (Pull Request)

1. 访问项目的GitHub/GitLab页面
2. 点击 "Pull Requests"
3. 选择一个待审查的PR

### Step 2: 快速浏览 (3分钟)

**看什么?**
- PR的标题和描述:了解改了什么
- 变更的文件数和行数:判断工作量
- 关联的Issue:了解背景和目标

**问自己:**
- 这次变更的目的是什么?
- 影响范围有多大?
- 是否需要我重点关注什么?

### Step 3: 逐文件审查 (15-30分钟)

**怎么看?**
1. 点击每个变更的文件
2. 使用diff视图查看修改内容
3. 对照审查清单检查

**看什么?**
- ✅ **逻辑正确吗?** - 业务逻辑是否正确实现
- ✅ **有安全问题吗?** - SQL注入、XSS、权限等
- ✅ **性能好吗?** - 有没有N+1查询、长事务
- ✅ **易读吗?** - 命名清晰、结构合理
- ✅ **有测试吗?** - 核心逻辑有测试覆盖
- ✅ **有文档吗?** - API文档、JavaDoc注释

### Step 4: 写评论 (5-10分钟)

**怎么写?**

```markdown
🔴 **Blocker: SQL注入风险**

第45行:用户输入直接拼接到SQL语句中。

**原因:**
攻击者可以通过构造特殊输入执行任意SQL命令,如:
`name = "'; DROP TABLE users; --"`

**建议修复:**
```java
// 使用MyBatis参数绑定
@Select("SELECT * FROM users WHERE name = #{name}")
User findByName(@Param("name") String name);
```

**优先级:** 🔴 必须立即修复
```

**评论模板**:
- 🔴 Blocker: 必须修复的严重问题
- 🟡 Major: 建议修复的重要问题
- 💭 Minor: 可选的改进建议
- ✅ 肯定: 指出好代码

### Step 5: 给出结论 (2分钟)

**审查结论**:
- ✅ **Approve** - 代码很好,可以直接合并
- 🟡 **Comment** - 有建议但不强制修改
- 🔴 **Request Changes** - 有问题需要修复后再次审查

**写总结**:
```markdown
## 审查总结

### 总体印象
代码结构清晰,设计合理。变更规模适中,测试覆盖较好。

### 关键问题
| 优先级 | 问题 | 建议 |
|--------|------|------|
| 🔴 | SQL注入风险 | 使用参数绑定 |
| 🟡 | N+1查询 | 使用JOIN优化 |

### 优点
- ✅ 异常处理完善
- ✅ 命名清晰易读
- ✅ 测试覆盖充分

### 结论
- [x] Request Changes - 修复后请@我重新审查
```

## 📋 日常使用

### 作为作者:提交PR前做什么

**必做清单** (5分钟):
```bash
# 1. 编译通过
mvn clean compile

# 2. 测试通过
mvn test

# 3. 代码风格检查
mvn checkstyle:check

# 4. 静态分析
mvn spotbugs:check

# 5. 自查编码规范
- 异常使用 BusinessException(ErrorCode.XXX)
- 随机数使用 ThreadLocalRandom
- 密码验证使用 passwordEncoder
- 事务只在原子操作上加
- 循环内日志用 debug 不用 info
```

**提交PR时**:
- 标题清楚: `[feat] 添加宠物进化系统`
- 描述完整: 变更说明、测试方法、影响范围
- 关联Issue: Fixes #123

### 作为审查者:日常审查怎么做

**快速流程** (20分钟):
1. 理解PR目的 (3分钟)
2. 浏览变更文件 (5分钟)
3. 详细检查代码 (10分钟)
4. 写评论和总结 (5分钟)

**重点检查**:
- Blocker问题: 安全、并发、数据一致性
- Major问题: 性能、代码质量、测试覆盖
- Minor问题: 代码风格、文档完整

## 🔥 常见问题速查

### Q1: 审查太慢怎么办?

**A: 使用快速检查清单**

```markdown
🚀 5分钟快速审查

**必看 (Blocker)**:
- [ ] 无SQL注入
- [ ] 无并发安全问题
- [ ] 事务边界合理
- [ ] 异常处理正确

**应看 (Major)**:
- [ ] 无N+1查询
- [ ] 核心逻辑有测试
- [ ] 命名清晰
- [ ] 无重复代码

**可选 (Minor)**:
- [ ] 代码风格
- [ ] 文档完整
```

**优先级**:
- 紧急PR: 只看Blocker
- 常规PR: Blocker + Major
- 重要PR: 全部检查

---

### Q2: 不会写评论怎么办?

**A: 使用标准模板**

**有问题**:
```markdown
🟡 **Major: [问题类型]**

[问题描述]

**建议:**
[修复方案]
```

**有疑问**:
```markdown
❓ 能否说明一下:

[你的问题]
```

**认可**:
```markdown
✅ **[优点]**

[具体描述],做得好!
```

---

### Q3: 发现的历史代码有问题,要一起修吗?

**A: 童子军规则**

**原则**:
- 如果修改相关代码,顺手修复
- 如果无关,另提PR

**示例**:
- 你改了用户注册功能,发现登录模块有个N+1问题 → 可以一起修复
- 你改了宠物功能,发现充值模块有个bug → 另提PR

---

### Q4: 审查意见有分歧怎么办?

**A: 先讨论,再决定**

**流程**:
1. 充分讨论技术方案
2. 各自说明理由
3. 如果无法达成一致:
   - 由资深开发者或架构师决定
   - 记录决策原因
   - 尊重最终决定

**示例**:
```
开发者A: 这里的循环用for更直观
审查者B: 用stream更函数式,性能更好
架构师: 项目统一用stream,保持一致性
结果: 按stream实现
```

---

### Q5: 紧急修复可以跳过审查吗?

**A: 可以事后审查

**流程**:
1. hotfix分支快速修复
2. 1人快速审查
3. 合并到生产
4. **24小时内补审查记录**
5. 复盘会议分析根因

## 🎓 进阶技巧

### 如何提高审查效率?

**1. 分批审查**
- 大型PR分多次审查
- 每次2-3个文件
- 避免疲劳

**2. 关注重点**
- 先看核心逻辑
- 再看边界条件
- 最后看细节

**3. 使用工具**
- IDE的diff功能
- GitHub的"Suggest Changes"
- 代码高亮和行号

**4. 提问先判**
- 不确定的地方先提问
- 不要直接假设错了
- 给作者解释的机会

**5. 记录问题**
- 边看边记录
- 最后整理成总结
- 便于快速回顾

---

### 如何减少审查轮次?

**1. 充分自测**
- 提交前完成所有检查
- 确保Blocker级别问题为0

**2. 清晰描述**
- PR描述清楚变更内容
- 说明测试方法
- 提供截图(如有UI变更)

**3. 主动沟通**
- 复杂逻辑提前沟通
- 设计方案先行讨论
- 避免方向性问题

**4. 小步提交**
- 一个PR一个功能
- 200-400行最佳
- 易于审查和理解

**5. 响应及时**
- 收到意见尽快修复
- 有疑问及时提问
- 保持沟通顺畅

### 如何写出好的评论?

**好的评论**:
```markdown
🟡 **Major: N+1查询问题**

`getPlayerQuestsDetail()`方法存在N+1查询。

**影响:**
如果玩家有50个任务,会产生51次数据库查询,响应时间随任务数线性增长。

**建议:**
使用JOIN一次性查询,性能提升50倍。

```java
<select id="selectQuestDetails" resultMap="QuestDetailResult">
    SELECT pq.*, q.* FROM player_quests pq
    LEFT JOIN quests q ON pq.quest_id = q.id
    WHERE pq.player_id = #{playerId}
</select>
```

**性能对比:**
- 当前: 50个任务 = 51次查询
- 优化后: 50个任务 = 1次查询
```

**差的评论**:
```markdown
❌ 这里有问题

❌ 改成JOIN

❌ N+1
```

**区别**:
- 好的评论: 说明问题、影响、解决方案、对比数据
- 差的评论: 只有结论,没有解释

## 📚 学习路径

### 新手 (0-1个月)

**目标**: 掌握基本审查能力

**学习内容**:
1. 阅读本快速上手指南 (30分钟)
2. 完成5个PR审查 (跟随导师)
3. 学习代码审查标准 (2小时)
4. 掌握常见问题识别 (1周)

**考核标准**:
- 能独立完成简单PR的审查
- 能识别Blocker和Major问题
- 能写出规范的审查评论

---

### 进阶 (1-3个月)

**目标**: 能独立审查复杂PR

**学习内容**:
1. 完成代码审查培训 (1周)
2. 独立完成20个PR审查
3. 参与架构变更审查 (跟随导师)
4. 总结优秀案例和常见问题

**考核标准**:
- 能独立审查复杂PR
- 能给出架构级建议
- 能指导和培训新手

---

### 高级 (3-6个月)

**目标**: 成为资深审查者

**学习内容**:
1. 完成50个PR审查
2. 参与规范制定和优化
3. 培训新的审查者
4. 建立优秀PR案例库

**考核标准**:
- 能审查架构级PR
- 能制定审查规范
- 能培训和指导他人
