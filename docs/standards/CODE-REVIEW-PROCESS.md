# 代码审查流程规范

> 定义代码审查的完整流程、角色职责和工具使用规范。

**作者**: shaun.sheng &nbsp;|&nbsp; **最后更新**: 2026-03-24

---

## 1. 流程概览

```
┌─────────────┐    ┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│  1. 开发完成  │ → │  2. 提交PR   │ → │  3. 代码审查  │ → │  4. 合并发布  │
└─────────────┘    └─────────────┘    └─────────────┘    └─────────────┘
       │                  │                  │                  │
       ▼                  ▼                  ▼                  ▼
  本地测试通过        填写PR模板         审查者检查          squash合并
  完成自查清单        关联Issue          作者修复           打标签
```

---

## 2. 详细流程

### 2.1 阶段一：开发完成

**开发者职责**：

1. **本地测试**
   ```bash
   # 运行单元测试
   mvn test
   
   # 启动服务验证
   mvn spring-boot:run
   
   # 手动测试关键路径
   ```

2. **完成自查清单**
   - 对照 [代码审查标准](./CODE-REVIEW-STANDARDS.md) 逐项检查
   - 确保无Blocker级别问题
   - 更新相关文档

3. **代码整理**
   ```bash
   # 格式化代码
   mvn spotless:apply
   
   # 检查代码风格
   mvn checkstyle:check
   
   # 清理无用导入
   # IDE: Optimize Imports
   ```

### 2.2 阶段二：提交PR

**PR标题格式**：
```
[类型] 简短描述

类型：feat/fix/docs/refactor/test/chore
示例：[feat] 添加宠物进化系统
```

**PR描述模板**：

```markdown
## 变更说明
[描述本次PR的主要变更]

## 关联Issue
Fixes #123

## 变更类型
- [ ] Bug修复
- [ ] 新功能
- [ ] 文档更新
- [ ] 代码重构
- [ ] 性能优化

## 检查清单
- [ ] 代码通过本地编译
- [ ] 新增功能有测试覆盖
- [ ] 所有异常使用BusinessException
- [ ] 新增ErrorCode已登记
- [ ] 相关文档已更新

## 测试说明
[如何测试这些变更]

## 截图（如适用）
[UI变更需要截图]
```

**分支命名规范**：
```
feature/xxx   # 新功能
fix/xxx       # Bug修复
hotfix/xxx    # 紧急修复
docs/xxx      # 文档更新
refactor/xxx  # 代码重构
```

### 2.3 阶段三：代码审查

#### 2.3.1 分配审查者

```markdown
**默认分配规则**：
- 后端代码 → 后端负责人
- 前端代码 → 前端负责人
- 跨模块变更 → 相关模块负责人共同审查
- 架构变更 → 架构师必须参与

**审查者数量**：
- 常规PR：1名审查者
- 核心模块变更：2名审查者
- 架构调整：架构师+1名模块负责人
```

#### 2.3.2 审查步骤

**第一步：快速浏览（5分钟）**
- 理解变更目的
- 检查变更范围是否合理
- 确认关联Issue

**第二步：详细审查（20-40分钟）**
- 逐文件检查代码
- 对照审查清单
- 记录问题和建议

**第三步：总结反馈（5分钟）**
- 整理发现的问题
- 按优先级分类
- 给出审查结论

#### 2.3.3 审查状态

| 状态 | 说明 | 下一步 |
|------|------|--------|
| 🟢 **Approved** | 无问题或只有Minor建议 | 作者可合并 |
| 🟡 **Comment** | 有建议但不强制修改 | 作者可选择性处理 |
| 🔴 **Request Changes** | 有Blocker/Major问题 | 作者必须修复后再次审查 |

### 2.4 阶段四：合并发布

**合并前检查**：
- [ ] 所有审查意见已处理或回复
- [ ] CI/CD检查通过
- [ ] 无冲突需要解决

**合并规范**：
```bash
# 使用squash合并，保持主线整洁
git merge --squash feature/xxx

# 提交信息格式
[feat] 添加宠物进化系统

- 实现宠物进化检查逻辑
- 添加进化成功属性加成
- 解锁进化后新技能

Fixes #123
```

**发布后**：
- 删除已合并的功能分支
- 更新CHANGELOG
- 通知相关方

## 3. 审查工具使用

### 3.1 GitHub/GitLab Code Review

**评论类型**：

```markdown
1. 单行评论：点击代码行左侧添加
2. 多行评论：拖动选择多行
3. 文件评论：点击文件标题处
4. PR总结评论：底部评论框
```

**建议功能**：
- 使用"Suggest Change"直接提出代码修改建议
- 使用"Resolve Conversation"标记已解决的问题
- 使用"Start Review"批量提交评论

### 3.2 本地审查工具

**IDE插件**：
```
IntelliJ IDEA:
- Code Review插件
- CheckStyle插件
- SonarLint插件

VS Code:
- GitLens
- Code Review
- ESLint
```

**命令行工具**：
```bash
# 统计变更
git diff --stat main...feature/xxx

# 查看特定文件变更
git diff main...feature/xxx -- src/.../PlayerService.java

# 检查代码风格
mvn checkstyle:check

# 静态分析
mvn sonar:sonar
```

## 4. 特殊情况处理

### 4.1 紧急修复流程

```
生产事故 → hotfix分支 → 快速审查(1人) → 合并 → 事后补审查
```

**要求**：
- 事后24小时内补审查记录
- 在CHANGELOG中标记为hotfix
- 复盘会议讨论根因

### 4.2 大规模重构

**分阶段审查**：
```
阶段1：设计审查（架构师）
阶段2：接口审查（模块负责人）
阶段3：实现审查（代码审查者）
```

**策略**：
- 拆分为多个小PR
- 每个PR聚焦一个模块
- 保持向后兼容

### 4.3 跨团队变更

**协调流程**：
```
1. 提前通知相关团队
2. 组织跨团队技术评审
3. 各团队指定审查代表
4. 统一合并时间窗口
```

## 5. 度量与改进

### 5.1 关键指标

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 审查响应时间 | < 24h | PR提交到首次审查 |
| 审查周期 | < 48h | PR提交到合并 |
| 缺陷逃逸率 | < 5% | 合并后发现的问题比例 |
| 审查参与度 | > 80% | 团队成员参与审查比例 |

### 5.2 定期回顾

**月度审查会议**：
- 审查质量分析
- 常见问题汇总
- 流程优化建议
- 优秀案例分享

**季度审查**：
- 指标达成情况
- 流程调整决策
- 工具升级评估

## 6. 审查者指南

### 6.1 审查者检查清单

```markdown
## 审查前
- [ ] 理解PR目的和背景
- [ ] 阅读关联的Issue/文档

## 审查中
- [ ] 检查代码正确性
- [ ] 检查代码风格规范
- [ ] 检查测试覆盖
- [ ] 检查性能影响
- [ ] 检查安全风险
- [ ] 检查文档更新

## 审查后
- [ ] 总结关键问题
- [ ] 给出明确的审查结论
- [ ] 设置合理的修复期限
```

### 6.2 审查技巧

**高效审查**：
1. **时间分配**：复杂逻辑多花时间，样板代码快速浏览
2. **工具辅助**：使用IDE跳转、搜索功能
3. **上下文理解**：不理解的地方先问清楚
4. **分批审查**：大量变更分多次审查

**沟通技巧**：
1. **先问后判**：不确定的地方先提问
2. **解释原因**：说明为什么这是问题
3. **提供方案**：不仅指出问题，也给建议
4. **认可优点**：肯定好的设计和实现

## 7. 作者指南

### 7.1 如何回应审查意见

**接受意见**：
```markdown
✅ "已修复，见 commit abc123"
✅ "已修改，将XXX改为YYY"
```

**解释不同意见**：
```markdown
🤔 "这里我考虑的是XXX，因为YYY。你觉得如何？"
🤔 "这个方案是考虑到ZZZ场景，是否需要补充注释说明？"
```

**请求澄清**：
```markdown
❓ "这个建议能否详细说明一下？"
❓ "能否提供一个代码示例？"
```

### 7.2 如何减少审查轮次

1. **PR粒度适中**：一个PR专注一个功能，200-400行最佳
2. **充分自测**：提交前完成自查清单
3. **清晰描述**：PR描述清楚变更内容和测试方法
4. **主动沟通**：复杂逻辑提前和审查者沟通
