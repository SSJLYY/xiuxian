# 代码审查快速检查清单

> 用于日常代码审查的快速参考工具

**作者**: shaun.sheng  
**创建日期**: 2026-03-26  
**用途**: PR审查、自查、代码评审

---

## 🔴 Blocker 级别检查项

### 安全问题
- [ ] **无SQL注入风险**: 所有数据库查询使用参数化或MyBatis绑定
- [ ] **无XSS漏洞**: 用户输出进行了转义或使用模板引擎自动转义
- [ ] **认证检查**: 敏感操作有权限验证
- [ ] **密码安全**: 使用 `passwordEncoder.matches()` 验证密码
- [ ] **无敏感信息泄露**: 日志、异常信息不包含密码、Token等敏感数据

### 并发安全
- [ ] **随机数正确**: 使用 `ThreadLocalRandom.current()`,不使用 `new Random()`
- [ ] **线程安全**: Service中无不安全的共享状态,并发集合使用正确
- [ ] **无竞态条件**: 多线程访问的共享变量有适当同步

### 数据一致性
- [ ] **事务边界**: 原子操作使用 `@Transactional`,查询操作不加事务
- [ ] **无数据丢失风险**: 关键数据操作有事务保护
- [ ] **幂等性**: 异步/定时任务有幂等性保护

### API兼容性
- [ ] **向后兼容**: 不删除或修改已发布的API接口
- [ ] **版本管理**: 破坏性变更增加了版本号或标记为废弃

### 异常处理
- [ ] **无裸RuntimeException**: 所有业务异常使用 `BusinessException(ErrorCode.XXX)`
- [ ] **无空catch块**: 异常被捕获并处理,不吞掉
- [ ] **无错误日志丢失**: `error` 日志必须带异常对象

---

## 🟡 Major 级别检查项

### 性能优化
- [ ] **无N+1查询**: 循环中不调用数据库查询,使用JOIN或批量查询
- [ ] **无长事务**: 事务方法不包含大量查询或外部调用
- [ ] **批量操作**: 大量更新/插入使用 `updateBatchById` 而非循环
- [ ] **缓存策略**: 高频查询有缓存考虑
- [ ] **分页查询**: 大表查询有分页(LIMIT)

### 代码质量
- [ ] **输入验证**: 方法参数有非空、范围校验
- [ ] **命名清晰**: 变量、方法名能表达意图,避免 `doSomething()`
- [ ] **无重复代码**: 相同逻辑提取为方法或工具类
- [ ] **方法长度**: 方法不超过50行,复杂方法拆分为小方法
- [ ] **参数数量**: 方法参数不超过5个,多用DTO

### 测试覆盖
- [ ] **核心逻辑有测试**: 重要业务逻辑有单元测试
- [ ] **边界情况有测试**: 空值、边界值有测试
- [ ] **异常路径有测试**: 异常情况有测试覆盖
- [ ] **测试覆盖率**: 新代码覆盖率 ≥ 60%

### 模块边界
- [ ] **无跨模块Mapper**: 非admin模块不直接使用其他模块的Mapper
- [ ] **模块依赖正确**: 通过Service接口调用其他模块,不直接访问内部实现

---

## 💭 Minor 级别检查项

### 代码风格
- [ ] **注释完整**: 公共方法有JavaDoc注释
- [ ] **Magic Number**: 魔法数字提取为常量
- [ ] **日志级别**: 循环内使用 `debug` 级别,不使用 `info`
- [ ] **Import规范**: 无通配符import,无未使用的import

### 可维护性
- [ ] **文档更新**: API变更更新了文档
- [ ] **ChangeLog记录**: 重要变更记录在变更日志
- [ ] **ErrorCoder登记**: 新增ErrorCode已在代码和文档中登记

### 最佳实践
- [ ] **Controller薄**: Controller只负责参数接收、用户获取、Service调用、返回包装
- [ ] **IP获取**: 使用 `RequestUtils.getClientIp()` 获取IP
- [ ] **返回格式**: 统一使用 `ApiResponse<T>` 返回

## 📋 按角色分类的检查清单

### 作者提交前自查

**代码质量**:
- [ ] 代码通过本地编译: `mvn clean compile`
- [ ] 单元测试通过: `mvn test`
- [ ] 测试覆盖率达标: `mvn jacoco:check` (≥60%)
- [ ] 代码风格检查通过: `mvn checkstyle:check`
- [ ] 静态分析通过: `mvn spotbugs:check`

**编码规范**:
- [ ] 异常处理正确: 使用 `BusinessException(ErrorCode.XXX)`
- [ ] 随机数使用 `ThreadLocalRandom.current()`
- [ ] 密码验证使用 `passwordEncoder.matches()`
- [ ] 事务边界合理: 只在原子写操作加 `@Transactional`
- [ ] 日志使用规范: 循环内无info,error带异常对象

**模块边界**:
- [ ] 无跨模块Mapper调用 (admin模块除外)
- [ ] 模块间通过Service接口访问

**文档更新**:
- [ ] API文档已更新 (如有接口变更)
- [ ] JavaDoc注释完整 (公共方法)
- [ ] 新增ErrorCode已登记

### 审查者审查清单

**快速浏览 (5分钟)**:
- [ ] 理解PR的目的和背景
- [ ] 检查变更范围是否合理

**正确性**:

- [ ] 无SQL注入、XSS等安全漏洞
- [ ] 敏感操作有权限检查
- [ ] 无敏感信息泄露

**性能**:
- [ ] 无N+1查询
- [ ] 无长事务
- [ ] 有必要的缓存

**可维护性**:
- [ ] 命名清晰,易于理解
- [ ] 无重复代码
- [ ] 代码结构合理

**测试**:
- [ ] 核心逻辑有测试
- [ ] 测试覆盖充分
- [ ] 边界情况有测试

**文档**:
- [ ] API文档已更新

- [ ] 整理发现的问题

### 新手友好型检查清单

**第一次写代码的同学,请按以下顺序检查**:

1. **最基本的要求** (必须):
   - [ ] 代码能编译通过
   - [ ] 没有明显的语法错误
   - [ ] 变量名和方法名能看懂是什么意思

2. **安全第一** (重要):
   - [ ] 不把用户输入直接拼接到SQL语句里
   - [ ] 不把密码明文存到数据库
   - [ ] 不在日志里打印密码等敏感信息

3. **异常处理** (重要):
   - [ ] 出错了不要吞掉,要抛出 `BusinessException`
   - [ ] 使用项目里定义的 `ErrorCode`,不要自己硬编码错误信息

4. **并发安全** (重要):
   - [ ] 需要随机数时用 `ThreadLocalRandom.current()`

5. **数据库操作** (重要):
   - [ ] 循环里不要调用数据库查询,会产生N+1问题
   - [ ] 批量操作用 `updateBatchById`,不要循环调用 `updateById`

6. **事务管理** (重要):
   - [ ] 只在真正需要原子操作的方法上加 `@Transactional`
   - [ ] 查询方法不要加事务

7. **日志规范** (重要):
   - [ ] 循环里用 `log.debug`,不要用 `log.info`
   - [ ] `log.error` 必须把异常对象传进去

8. **Controller规范** (重要):
   - [ ] Controller里不要写业务逻辑
   - [ ] 只做: 接收参数 → 调用Service → 返回结果

9. **测试** (推荐):
   - [ ] 核心逻辑写个单元测试

10. **文档** (推荐):
    - [ ] 公共方法写个JavaDoc注释
    - [ ] 改了API要更新文档

## 🚀 特殊场景检查清单

### 热修复 (Hotfix) PR

**快速检查清单**:
- [ ] 修复范围最小化,只改必要的代码
- [ ] 已测试修复效果,不会引入新问题
- [ ] 至少1人审查通过
- [ ] CI/CD检查通过
- [ ] 已在测试环境验证

**允许的临时措施**:
- [ ] 可以临时降低测试覆盖率要求
- [ ] 可以临时放宽代码风格要求
- [ ] 可以在24小时内补充完整文档

**后续工作**:
- [ ] 24小时内补全代码审查
- [ ] 根因分析,防止再次发生
- [ ] 复盘会议,改进流程

---

### 架构调整 PR

**额外检查项**:
- [ ] 有架构设计文档
- [ ] 有迁移路径和回滚方案
- [ ] 至少2名资深开发者审查
- [ ] 架构师参与审查
- [ ] 有性能测试数据支持

**向后兼容性**:
- [ ] 不破坏现有API
- [ ] 或提供了兼容层
- [ ] 或给出了迁移方案

---

### 重构 PR

**检查项**:
- [ ] 重构前后功能等价(有测试证明)
- [ ] 没有引入新的bug
- [ ] 代码结构更清晰
- [ ] 可维护性提升
- [ ] 有重构前后对比

## 💡 使用技巧

### 高效审查技巧

1. **分批审查**: 大型PR分多次审查,每次2-3个文件
2. **关注重点**: 先看核心逻辑,再看细节
3. **使用工具**: 用IDE的diff功能,快速定位变更
4. **提问先判**: 不确定的地方先提问,不要直接假设错了
5. **记录问题**: 边看边记录,最后整理成总结

### 减少审查轮次技巧

1. **充分自测**: 提交前完成所有检查清单
2. **清晰描述**: PR描述清楚变更内容和测试方法
3. **主动沟通**: 复杂逻辑提前和审查者沟通
4. **小步提交**: 一个PR专注一个功能,200-400行最佳
5. **响应及时**: 收到审查意见尽快修复和回应

### 沟通技巧

1. **提问而非指责**: "这里是否考虑用JOIN优化?" 比 "这里有问题" 更好
2. **解释原因**: 不仅说问题是什么,还要说为什么
3. **提供方案**: 不仅指出问题,也给解决方案
4. **认可优点**: 肯定好的设计和实现
5. **保持尊重**: 即使有分歧,也要尊重对方
