# Project Development Direction

## 目标

把模糊的“接下来做什么”整理成可执行的阶段计划，而不是泛泛 roadmap。

## 使用场景

- 用户要求做开发规划、路线图、阶段目标。
- 需求很多，需要区分 `MVP`、`Next`、`Later`。
- 需要决定先做哪个功能。
- 需要把一批想法拆成 1 到 2 周的可执行迭代。

## 规划前先对齐

- 当前项目是单仓前后端协作，不是独立前后端分离工程。
- 新玩法通常需要后端接口和静态前端页面一起落地。
- 优先围绕真实用户路径排顺序，不按“哪个系统看起来高级”排顺序。
- 每个阶段都要带验证和文档更新，不接受只列功能名。

## 默认规划步骤

1. 定义当前阶段的一句话目标。
2. 列出候选需求并按 `MVP`、`Next`、`Later` 分类。
3. 明确本轮不做项，防止范围蔓延。
4. 规划 2 到 4 个里程碑。
5. 为当前迭代拆出 3 到 5 个具体任务。
6. 给每个任务补上产出、验证方式和落地路径。

如果需要更细的规划检查项，读取 `references/planning-checklist.md`。

## 优先级原则

按这个顺序取舍：

1. 主流程可用性
2. 用户成长反馈是否清晰
3. 系统稳定性与一致性
4. 内容密度
5. 技术完善度

## 输出模板

```markdown
## 当前阶段目标
- ...

## 范围划分
- MVP: ...
- Next: ...
- Later: ...
- 本轮不做: ...

## 里程碑
1. ...
   - 目标：...
   - 关键任务：...
   - 完成定义：...
2. ...

## 当前迭代
- [ ] 任务 1：产出 + 验证
- [ ] 任务 2：产出 + 验证
- [ ] 任务 3：产出 + 验证

## 风险与应对
- ...
```

## 约束

- 不输出空泛建议。
- 不同时推进过多主线。
- 每轮必须有“本轮不做”。
- 每个里程碑至少包含代码、验证、文档三个维度。
